2. RBAC Plan Review — What's Right, What's Broken, What's Missing
2.1 What the Plan Gets Right
Two-axis model is correct. planIncludes(feature) AND roleAllows(action) are independent gates. Do not conflate them.
Four canonical roles (OWNER/ADMIN/MEMBER/VIEWER) map cleanly to real battery compliance team functions: founder, compliance lead, operator, auditor.
Supplier as external persona is correct — not an internal seat, not subject to internal RBAC.
Per-request plan lookup is correct — plan should not be in JWT. Upgrades must take effect immediately, not at next token refresh.
Phase 0 first (bug fix before entitlements) is the right sequence. You cannot build correct entitlements on a broken RBAC base.
402 vs 403 error shape distinction is well-designed. 402 + required_plan + upgrade_url renders an upgrade prompt. 403 renders 'insufficient role' — different UI, different action for the user.

2.3 Five Gaps Not in the Current Plan
Gap 1: Passport Quota Enforcement (Critical)
No quota middleware exists. Without it, all plans are functionally equivalent — a Starter tenant can issue unlimited passports. Required: QuotaService tracking tenant_id → monthly_passport_count, and a RequireQuota() middleware on POST /passports that returns 402 { quota_used, quota_limit, overage_url } when exceeded.
Gap 2: Overage Policy
Starter: hard block at quota. Price-sensitive SMEs need billing predictability.
Growth: soft overage at ₹8/passport, billed at month end. Production compliance deadlines cannot wait for an upgrade click.
Enterprise: negotiated overage rate in contract.
Gap 3: Free Trial Strategy
No trial tier defined. Critical for Indian B2B — procurement cycles are long, buyers need hands-on evaluation, and no-credit-card is essential (card trust and limits are real friction in India). Recommendation: 14-day Growth trial on signup, no credit card, 100 passport cap. At day 14 auto-downgrade to Starter if no plan selected. All data preserved.
Gap 4: Audit Log for Role Changes
Compliance SaaS must log every role change (invite, promote, demote, remove) to an immutable team_audit_log table: actor, subject, old_role, new_role, timestamp. Enterprise buyers and EU auditors will ask for this.
Gap 5: ABAC Extension Path (Future)
Current RBAC assumes all MEMBERs in a tenant see all data. At enterprise scale (Amara Raja factory A vs factory B), you need attribute-based checks. Design resource-level attributes into the data model now; implement them when the first Enterprise customer asks. Do not implement today — that is premature.

3. PBAC — Policy-Based Access Control
3.1 PBAC Is Already Partially Implemented
The middleware chain Protect → RequireOnboardingComplete → RequireFeature(x) → RequireRole(y) IS a policy-based access control system — just expressed as imperative middleware rather than a declarative policy. The existing plan recognizes this pattern. The gap is that it is scattered across 10+ call sites without a single source of truth.
3.2 The Five Policy Axes

3.3 Recommended Architecture
Create a single PolicyService in internal/services/policy.go that composes the five axes. Each protected route calls policy.Evaluate(ctx, feature, action) → {Allow, Deny, Reason}. This centralizes all access decisions and makes the policy auditable and testable in one place.
Do NOT adopt a full policy engine (OPA, Casbin) yet. That is 3× the implementation cost for the same result at current scale. The Go-native middleware composition is sufficient. Casbin becomes valuable when Enterprise ABAC (factory-level segmentation) is needed.

4.4 India-Specific Pricing Dynamics
Indian B2B buyers expect to pay 40–60% of EU/US list price. Enterprise buyers are within 2× of global pricing.
Buyers expect 20–30% negotiation room. List at targets that survive a 25% discount in direct sales.
Annual billing discount of 15–20% is standard. Improves cashflow and reduces churn.
No credit card required for trial is essential — card friction and trust are real barriers in India.
Usage-based billing (quota per passport) is gaining acceptance and aligns price with value delivered.

5. Pricing Tiers
5.1 Model: Flat Subscription + Passport Quota
ExportReady uses a hybrid model: flat monthly subscription to unlock features, plus a passport issuance quota. This works because passport creation is the core value metric (EU compliance deadline drives passport demand), while feature unlocking (India vs EU compliance) is a binary plan gate.
Avoid per-seat as the primary meter. Indian buyers resist per-seat SaaS — they feel every additional user as a direct cost. For a compliance platform, seat count is not a value metric. Use quota instead.

6. Feature → Tier Map (Definitive)
6.1 The EU Compliance Question
Should EU Compliance be in Starter? No. Here is the rationale:
EU export = Growth customer. Any manufacturer seriously pursuing EU export has revenue above ₹50 crore. They can afford Growth. Starter is for domestic-market or pre-export companies.
The upgrade trigger is: 'I need to issue DPPs for my EU shipments.' India compliance in Starter → see EU preview → upgrade to Growth → issue first DPP. This is a clean, compelling, deadline-driven upgrade path.
Exception: Carbon Calculator stays in Starter as a preview tool. Users see their battery's JRC carbon class without issuing an official certified DPP. This creates the aha moment that drives Growth upgrade.

7. Implementation Roadmap for Opus 4.8
Phase 0 — RBAC Bug Fix (Ship First, 1–2 Days)
Standardize UPPERCASE everywhere: auth_service.go JWT emission, all 10 RequireRole() sites in main.go, dispatch-page.tsx, lifecycle-page.tsx.
SQL migration: UPPER(role) on users and team_members tables; operator → MEMBER mapping.
Users get corrected JWT on next login. No forced logout needed.
Verification: ADMIN-role team member can hit admin-gated API routes. OWNER can use dispatch and lifecycle bulk ops.

Phase 1 — Plan Entitlement Backend (1 Week)
internal/services/entitlements.go — Feature → minPlan map (single source of truth).
RequireFeature(feature) middleware — DB plan lookup (Redis cached 60s), returns 402 {feature, required_plan, upgrade_url} if not entitled.
QuotaService — monthly passport counter per tenant. RequireQuota() middleware returns 402 {quota_used, quota_limit, overage_url} when exceeded. Hard block for Starter; soft overage for Growth.
Wire RequireFeature on all Growth+ routes: eu-compliance, mass-balance, due-diligence, dgft-claims, fleet, telemetry, partners, api-keys, webhooks.
Drop duplicate Tier field from models.go. PlanType is the single source.
GET /api/v1/quota endpoint: {used, limit, resets_at, plan} for Billing page display.

Phase 2 — Frontend Gating (1 Week)
Add plan_type to /auth/me response and User interface in auth-context.tsx.
Build useEntitlements() hook → { has(feature), can(action), plan, role } backed by a config mirroring backend Feature → minPlan.
Extend NavItem in lib/products.ts with feature and minRole fields. Sidebar shows locked items with padlock + 'Available on Growth' chip — do not hide, show value.
Replace all ad-hoc user.role === checks with can() from useEntitlements(). Fix the 4 known broken checks.
Build upgrade interstitials: locked feature page renders 'Available on Growth — Upgrade' full-page prompt with feature summary and link to Billing.

Phase 3 — Hardening (3–5 Days)
Integration tests: STARTER tenant gets 402 on Growth routes; VIEWER gets 403 on write actions; unauthenticated gets 401.
Audit log: write all role changes (invite, promote, demote, remove) to team_audit_log table.
Trial expiry: auto-downgrade at day 14 preserves data, restricts Growth features, shows upgrade prompt.
Quota reporting: Billing page shows quota ring (used/limit/resets_at).
